# Deploying BDQ content to rs.tdwg.org

## Source of this document

This is an analysis produced by GitHub Copilot of the friction produced by the bdqffdq.owl ontology and the multiplicity of terms in the bdqtest vocabulary for deployment on rs.tdwg.org and how this friction might be approached.

## Scope and source context

This note describes how the `tdwg/rs.tdwg.org` repository currently stores source metadata and generates/publishes machine-readable and human-readable representations of TDWG standards components, and what changes would be required to support the BDQ vocabularies. It focuses on two BDQ deliverables:

1. serving a Turtle serialization of the `bdqffdq.owl` ontology; and
2. generating RDF representations of `bdqtest:` Tests from source data that include repeated and one-to-many relationships.

For BDQ, the authoritative source tree is the `tdwg/bdq` repository under `tg2/_review`, including `tg2/_review/vocabulary/bdqffdq.owl` and `tg2/_review/vocabulary/bdqtest_term_versions.csv`. The BDQ build system also includes generation, audit, and validation scripts under `tg2/_build_review` and `tg2/_make_review`. See `tg2/_make_review/copy_files.sh:11-13`, `53-61`; `tg2/_make_review/do_build.sh:7-30`; `.github/workflows/pages.yml:43-50`, `91-99`, `128-145`.

---

## Executive summary

`rs.tdwg.org` is fundamentally a **CSV/YAML-driven metadata publishing system**, not a general RDF graph host. Its normal workflow is:

1. maintain authoritative CSV/YAML metadata;
2. run Python processing to generate current-term, version, hierarchy, redirect, and index CSV tables;
3. load those CSV files into BaseX as XML;
4. generate RDF/HTML dynamically through XQuery and content negotiation.

This architecture works well for TDWG term lists and document metadata, but BDQ introduces two important kinds of friction:

- `bdqffdq.owl` is a true RDF/OWL ontology, not just a flat term list. It contains ontology-level metadata, OWL restrictions, blank-node structures, and general axioms that are not naturally represented by the current row/column mapping model (`tg2/_review/vocabulary/bdqffdq.owl:12-16`, `209-242`, `335-339`, `1421-1439`).
- `bdqtest` source data contains many repeated and one-to-many relationships that cannot be losslessly represented by the current “one populated cell -> one emitted property value” mapping model without either:
  - introducing BDQ-specific parsing logic, or
  - normalizing the source into multiple linked CSV tables using the existing `linked-classes.csv` mechanism.

The **minimal pragmatic implementation** is to publish BDQ RDF artifacts as authoritative static files or dedicated special cases, rather than forcing them through the generic rs.tdwg.org table-generation pipeline. The **more general architectural implementation** is to extend rs.tdwg.org so it can ingest RDF-native resources and/or more systematically support repeatable child resources through linked tables.

## 1. Current rs.tdwg.org architecture

### 1.1 Authoritative source model

The rs.tdwg.org workflow assumes that authoritative metadata is maintained as CSV plus configuration/mapping files. The processing documentation explicitly describes a workflow where hand-edited CSV and YAML metadata are combined to generate the underlying authoritative CSV files used to build both machine-readable and human-readable outputs (`process/process-vocabulary.md:41-67`).

The main processing script is `process/process.py`. It:

- generates or updates current term metadata;
- generates term-version metadata;
- updates term-list metadata and version membership;
- propagates changes up to vocabulary and standard metadata;
- updates redirect configuration for HTML dereferencing.

Key code paths include:

- term-version generation: `process/process.py:232-333`
- current-term generation and term-list/index updates: `process/process.py:336-675`
- main namespace loop and hierarchy propagation: `process/process.py:1218-1319`

Version IRIs are generated by appending the issue date to the term local name, and replacement links are generated automatically (`process/process.py:280-296`; see also `process/process-vocabulary.md:208-215`).

### 1.2 BaseX loading and runtime publication

The repository does not store RDF as its publication database. Instead, CSV files are loaded into BaseX as XML during initialization:

- database startup and import: `docker/initialize-database.sh:23-32`
- loading `constants.csv`, auxiliary CSVs, core metadata, and linked metadata into XML: `index/load-db-from-github.py:208-252`

At runtime, XQuery in `html/restxq.xqm` performs dereferencing and serialization:

- dataset dumps: `html/restxq.xqm:29-74`
- representation selection and response generation: `html/restxq.xqm:1054-1100`
- 303 content-negotiation redirects: `html/restxq.xqm:1177-1237`
- record and linked-resource RDF generation: `html/restxq.xqm:1688-1805`
- per-column property emission: `html/restxq.xqm:1961-2003`

HTML output advertises alternate serializations via `.htm`, `.ttl`, `.rdf`, and `.json` links (`html/html.xqm:395-403`).

### 1.3 Validation currently in rs.tdwg.org

Existing validation is focused on dereferencing and content negotiation rather than ontology semantics or SHACL validation. The current dereferencing test probes multiple Accept headers for example URLs from each database and from document IRIs (`index/dereferencing-test.py:7`, `26-60`, `63-148`).

## 2. What the current rs.tdwg.org data model assumes

### 2.1 One column maps to one property occurrence

The basic mapping model is explicit in the standard term mapping template:

`header,predicate,type,value,attribute,subject_id`  
(`process/files_for_new/current_terms/simple-vocabulary-column-mappings.csv:1-19`)

At serialization time, `html/restxq.xqm` iterates over columns and mapping rows, and if a cell is non-empty, emits exactly one literal or IRI value for that mapped property (`html/restxq.xqm:1974-1990`).

This means that, by default, the system assumes:

- one relevant value per populated cell;
- one mapping row per emitted property occurrence;
- no generic splitting of comma-separated, bracketed, or otherwise compound cell content into multiple RDF assertions.

This is the key technical reason that BDQ repeated relationships do not fit natively in a single source table row.

### 2.2 Multiplicity is handled today by extra tables, not repeated cells

rs.tdwg.org already has a mechanism for one-to-many relationships, but it is not cell-based. It uses:

- a root dataset;
- auxiliary child CSV tables;
- `linked-classes.csv` to describe how those child tables link to the root;
- XQuery that walks those linked child resources and emits both forward and backward RDF links.

Examples:

- documents link to authors, formats, and versions through `docs/linked-classes.csv:1-4`
- term lists link to versions and members through `term-lists/linked-classes.csv:1-3`
- linked-resource generation logic appears in `html/restxq.xqm:1739-1800`
- linked metadata is specially loaded into BaseX in `index/load-db-from-github.py:247-252`

So the repository already contains the right **mechanism** for multiplicity, but not yet a BDQ-specific **schema** using that mechanism.

### 2.3 Existing repeatability signals do not solve RDF multiplicity

Some vocabularies include metadata columns like `tdwgutility_repeatable`, but those are simply published as metadata properties; they do not change how runtime RDF emission works (`process/create-vocabulary.md:102-106`; example mapping rows such as `tdwgutility_repeatable,tdwgutility:repeatable,plain,,,$root` appear across vocabulary files). The serializer still treats a populated cell as one property value (`html/restxq.xqm:1974-1990`).

So current rs.tdwg.org does **not** provide a generic, lossless mechanism for repeated values inside one CSV cell.

## 3. Why `bdqffdq.owl` does not fit the ordinary term-list model

### 3.1 `bdqffdq.owl` is an ontology, not just a term list

The ontology begins with ontology-level assertions:

- ontology IRI typed as `owl:Ontology`
- `owl:versionIRI`
- `dcterms:issued`
- ontology-level notes and label

See `tg2/_review/vocabulary/bdqffdq.owl:12-16`.

This differs from the ordinary rs.tdwg.org term-list pattern, where metadata is stored as tabular rows for terms, term versions, term lists, vocabularies, and standards, then reassembled into RDF at request time (`process/process.py:232-333`, `336-675`, `1218-1319`; `process/process-vocabulary.md:57-67`).

### 3.2 The ontology contains RDF/OWL structures that are awkward in the current model

The ontology includes:

- object properties with anonymous `owl:Restriction` range expressions (`bdqffdq.owl:209-242`, `335-339`)
- subclass structures and ontology classes (`bdqffdq.owl:603-840`)
- general axioms with `owl:AllDisjointClasses` and `owl:members` RDF lists (`bdqffdq.owl:1421-1439`)

These structures are not naturally modeled as “one row = one described root resource with mapped columns”, especially when the graph includes anonymous nodes and RDF collections.

### 3.3 Consequence

There is no existing rs.tdwg.org pathway that says “take this RDF file and publish its triples unchanged through the same database-backed negotiation system.” The closest precedent is not native ingestion, but bespoke redirect logic for externally hosted ontologies such as ABCD (`html/restxq.xqm:772-809`).

So while rs.tdwg.org can serve Turtle and RDF/XML, its normal publication path assumes tabular source data, not an already-authored ontology graph.

## 4. Why `bdqtest` does not fit a single-table current-term model

### 4.1 The source data contains repeated and structured relationships

The `bdqtest_term_versions.csv` header already shows a richer model than a normal TDWG term-list row. It includes fields such as:

- `InformationElement:ActedUpon`
- `aggregatesResponsesFrom`
- `InformationElement:Consulted`
- `Parameters`
- `AuthoritiesDefaults`
- `References`
- `Example Implementations (Mechanisms)`
- `UseCases`
- `ArgumentGuids`

See `tg2/_review/vocabulary/bdqtest_term_versions.csv:1`.

Concrete examples from current rows show multiple values in single fields:

- multiple acted-upon information elements: `dwc:minimumDepthInMeters,dwc:maximumDepthInMeters` (`bdqtest_term_versions.csv:4`)
- multiple acted-upon and consulted information elements in the same row (`bdqtest_term_versions.csv:10`, `24`, `29`)
- multiple parameters (`bdqtest_term_versions.csv:23`)
- multiple Use Cases and multiple examples are common in the current content
- references may be supplied as HTML list content containing multiple URLs

### 4.2 BDQ already requires custom parsing logic

The BDQ Python RDF builder explicitly performs semantics that rs.tdwg.org does not currently perform generically:

- split information-element CSV lists into multiple IRIs: `tg2/_build_review/build_bdqtest_rdf.py:474-504`
- create special MultiRecord aggregated acted-upon nodes: `507-541`
- parse HTML/plaintext references into multiple `dcterms:references` links: `137-176`, `739-744`
- parse multiple examples from `[...],[...]` syntax: `181-203`, `797-799`
- create `bdqffdq:Argument` nodes by pairing `ArgumentGuids` with `Parameters`: `580-618`, `809`
- collect repeated `UseCases` into policy collections and create UseCase / Policy resources: `811-850`
- serialize to Turtle, RDF/XML, and JSON-LD: `855-865`

The script documentation is explicit that it is a replacement for the prior Java/kurator-ffdq workflow and derives argument details directly from the term-version CSV plus auxiliary GUID files (`tg2/_build_review/build_bdqtest_rdf.py:1-40`, `875-910`).

### 4.3 Consequence

If `bdqtest_term_versions.csv` were pushed through the current rs.tdwg.org serializer without additional modeling, many repeated relationships would collapse into opaque string literals. That would not be a lossless or semantically adequate publication of `bdqtest`.

## 5. Using the existing `linked-classes.csv` mechanism for BDQ multiplicity

The existing `linked-classes.csv` mechanism is the most natural rs.tdwg.org-native way to represent BDQ multiplicity without inventing a completely new publication model.

### 5.1 Why linked classes are a good fit

The current mechanism already supports:

- root resources with one-to-many child resources;
- child resource IRIs or blank nodes;
- link properties from child back to root;
- optional forward links from root to child;
- independent column mappings for each linked child class.

See:

- examples in `docs/linked-classes.csv:1-4` and `term-lists/linked-classes.csv:1-3`
- runtime generation in `html/restxq.xqm:1739-1800`
- linked metadata load in `index/load-db-from-github.py:247-252`

This is exactly the kind of structure needed for BDQ Tests, where a single test has many:

- acted-upon information elements
- consulted information elements
- argument nodes
- references
- examples
- use-case/policy relationships
- possibly mechanism/source-code links
- possibly aggregated-response support nodes for MultiRecord measures

### 5.2 Suggested BDQ normalization using linked classes

A plausible rs.tdwg.org-native model for `bdqtest` would use a root test/version table plus separate child tables such as:

- `bdqtest.csv` or `bdqtest-versions.csv` for root test/version metadata
- `bdqtest-actedupon.csv`
- `bdqtest-consulted.csv`
- `bdqtest-arguments.csv`
- `bdqtest-references.csv`
- `bdqtest-examples.csv`
- `bdqtest-usecases.csv`
- `bdqtest-policies.csv`
- `bdqtest-specifications.csv`
- optionally `bdqtest-implementations.csv` or `bdqtest-mechanisms.csv`

Each of those would be declared in a `linked-classes.csv` file for the BDQ dataset. The runtime XQuery already knows how to emit linked resources described by such tables (`html/restxq.xqm:1739-1800`).

### 5.3 What this would preserve well

Using linked classes would allow rs.tdwg.org to represent:

- multiple `bdqffdq:hasActedUponInformationElement` assertions
- multiple `bdqffdq:hasConsultedInformationElement` assertions
- multiple examples as repeated `skos:example`
- multiple references as child `dcterms:BibliographicResource` resources
- multiple arguments, each linked to a parameter and argument value
- multiple use-case / policy relationships

This would be much closer to the current BDQ RDF graph than storing comma-separated values in single cells.

### 5.4 What still does not fit perfectly

Even with linked classes, some BDQ constructs remain awkward:

- policy aggregation logic is derived from repeated use-case memberships and policy-type classification, not merely literal row expansion (`build_bdqtest_rdf.py:811-850`)
- MultiRecord measures use special derived acted-upon nodes based on `aggregatesResponsesFrom` (`507-541`)
- the ontology itself (`bdqffdq.owl`) still contains graph-native OWL axioms that should not be remodeled into linked CSVs if avoidable

So linked classes are a strong fit for `bdqtest`, but not a complete solution for `bdqffdq.owl`.

## 6. Need to generate BDQ CSV publication tables from RDF-maintained sources

A key architectural point is that future BDQ maintenance may increasingly occur in RDF/OWL-native form rather than by direct editing of rs.tdwg.org-style CSV tables. If so, and if rs.tdwg.org remains CSV-driven, then **publication CSVs will need to be generated from RDF source representations**.

This is especially important if new tests are authored or maintained as RDF descriptions that express:

- test individuals
- specifications
- argument nodes
- information-element relationships
- policy/use-case links
- references
- examples
- aggregation relations

In that case, rs.tdwg.org should not be treated as the source-of-truth editing format for BDQ. Instead:

1. BDQ-maintained RDF/OWL remains authoritative in `tdwg/bdq`;
2. a build step generates rs.tdwg.org publication CSVs and linked child CSVs from that RDF;
3. rs.tdwg.org then publishes those CSV-derived resources using its existing BaseX/XQuery machinery.

This is consistent with the existing BDQ practice of building publication artifacts from canonical source files in `_review` through explicit scripts (`tg2/_make_review/copy_files.sh:11-13`, `53-61`; `tg2/_make_review/do_build.sh:7-30`; `.github/workflows/pages.yml:43-50`).

In other words, if rs.tdwg.org uses linked-class CSVs for BDQ, those CSVs should likely be considered **derived publication artifacts**, not the editorial master.

## 7. Serving Turtle for `bdqffdq.owl`

### 7.1 Minimal pragmatic approach

The simplest correct approach is to publish `bdqffdq.owl` as an authoritative RDF file and expose a `.ttl` alias for content-type convenience, exactly as the BDQ GitHub Pages workflow already does:

- copy `_review` into the publication tree
- if `bdqffdq.owl` exists, copy it to `bdqffdq.ttl`
- verify that the `.ttl` file exists

See `.github/workflows/pages.yml:91-99`, `128-145`.

This preserves the ontology graph unchanged and avoids trying to rebuild OWL axioms from tables.

### 7.2 rs.tdwg.org implications

In rs.tdwg.org terms, that implies either:

- a static-file publication path for `bdqffdq.owl` and `bdqffdq.ttl`; or
- custom route logic similar to the ABCD special-case redirects that can return the ontology file directly instead of querying a BaseX database (`html/restxq.xqm:772-809`).

### 7.3 Why this is preferable

Trying to remodel the ontology into ordinary term and version tables would require inventing a tabular representation for:

- the ontology node itself
- blank-node restriction expressions
- `owl:AllDisjointClasses`
- RDF collection membership in `owl:members`
- and potentially future ontology extension axioms

That is theoretically possible, but it is far more work and risk than simply treating the ontology as the RDF-native artifact it already is.

## 8. Minimal pragmatic implementation vs general architectural implementation

## 8.1 Minimal pragmatic implementation

The minimal path is:

1. **Publish `bdqffdq.owl` directly**, with a `.ttl` alias or equivalent route.
2. **Publish `bdqtest.ttl`, `bdqtest.xml`, and `bdqtest.json` directly** as BDQ-built artifacts.
3. Add BDQ-specific dereferencing tests in rs.tdwg.org.
4. Optionally add lightweight BDQ-specific redirect/route logic in rs.tdwg.org if these resources must live under rs.tdwg.org-style endpoint conventions.

Advantages:

- preserves current BDQ semantics
- does not require extending `process.py`
- does not require inventing complex CSV schemas for OWL axioms
- aligns with current BDQ Pages build practice

Disadvantages:

- BDQ becomes a special case rather than a fully native rs.tdwg.org dataset
- less reuse of the generic rs.tdwg.org metadata hierarchy machinery

## 8.2 More general architectural implementation

A more ambitious path would extend rs.tdwg.org to support BDQ natively:

1. add a publication mode for RDF-native inputs such as TTL/OWL;
2. add BDQ dataset schemas using linked child tables for repeated structures in `bdqtest`;
3. generate those publication CSV tables from BDQ RDF source during build;
4. optionally extend the pipeline so term-version source can begin from richer RDF rather than only diff-style current-term CSVs.

Advantages:

- makes BDQ look more like a first-class rs.tdwg.org dataset
- reuses existing linked-class serialization logic
- creates a pattern potentially useful for other graph-richer standards

Disadvantages:

- materially expands rs.tdwg.org’s architecture
- requires schema design, build-script work, and more testing
- still does not fully eliminate the special handling needed for ontology-native OWL graphs

- Add one or more new BDQ datasets if BDQ content is loaded into BaseX as first-class rs.tdwg.org databases.

### 9.5 `index/load-db-from-github.py`

**General path**

  - configuration/constants

  - linked classes (`index/load-db-from-github.py:208-252`)
- However, new BDQ dataset directories and CSV schemas will need to conform to the loader’s expectations.

**If RDF-native ingestion is desired**
- This file would need substantive extension, because it currently assumes CSV-based inputs rather than RDF files.

### 9.6 `process/process.py`

**Minimal path**
- No change should be required if BDQ artifacts are published as externally built/static RDF files.

**General path**
- If maintainers want BDQ to be generated through the same hierarchy pipeline as other TDWG vocabularies, `process.py` would need significant enhancement.
- In particular, the current pipeline assumes:
  - current-term style modifications input
  - term-version IRI generation by appending dates
  - propagation through term-list/vocabulary/standard structures
  (`process/process.py:232-333`, `336-430`, `1218-1319`)
- BDQ test data and ontology data do not fit that model directly, so changes here would likely be larger than desirable unless limited to metadata bookkeeping around already-generated BDQ publication tables.

### 9.7 `process/process-vocabulary.md`

Update documentation to explain that BDQ differs from ordinary TDWG term-list processing because:

- `bdqffdq` is an ontology-native RDF/OWL artifact;
- `bdqtest` may require linked child tables for multiplicity;
- rs.tdwg.org publication tables may be generated from BDQ-maintained RDF/OWL source rather than hand-edited current-term CSVs.

Relevant current workflow assumptions appear in `process/process-vocabulary.md:41-67`, `73-75`, `206-222`.

### 9.8 `process/create-vocabulary.md`

Add a note that the normal guidance about adding columns to current-term/version files (`process/create-vocabulary.md:69-77`) is not sufficient for graph-rich standards like BDQ, where one-to-many relationships should be modeled with linked tables rather than comma-packed cells.

### 9.9 New BDQ dataset directories and schema files

**General path**
Create new dataset directories under rs.tdwg.org, likely including:

- a root BDQ dataset directory
- column-mappings CSV(s)
- classes CSV(s)
- constants CSV
- linked-classes CSV
- child CSV tables for acted-upon IEs, consulted IEs, arguments, references, examples, use cases, policies, etc.

These would reuse the established dataset structure already used elsewhere in the repository.

### 9.10 `html/redirects.csv`

If BDQ HTML pages are generated or redirected through rs.tdwg.org, add redirect records for the BDQ databases, consistent with existing redirect behavior (`process/process.py:632-673`; `html/restxq.xqm:1103-1125`).

### 9.11 `docker/initialize-database.sh`

No logic change should be required unless the initialization flow changes. If BDQ is represented as standard rs.tdwg.org datasets, the existing startup/import path should handle them once they are listed and structured correctly (`docker/initialize-database.sh:23-32`).

## 10. Recommended implementation approach

### Recommendation

The recommended approach is:

1. **Treat `bdqffdq.owl` as authoritative RDF/OWL and publish it directly**.
2. **Treat `bdqtest` RDF serializations as generated artifacts built from BDQ source in `tdwg/bdq`**, not as hand-maintained rs.tdwg.org CSV master data.
3. If deeper rs.tdwg.org integration is desired for `bdqtest`, **use the existing `linked-classes.csv` mechanism** to model multiplicity, but **generate those linked CSV publication tables from RDF-maintained BDQ source**, not by manually editing rs.tdwg.org tables.
4. Avoid trying to remodel the ontology graph itself into ordinary rs.tdwg.org term-list tables.

This gives the best balance of correctness, maintainability, and fit with the current architecture.

## 11. Open questions for maintainers

The following decisions should be made explicitly before implementation:

1. **Is rs.tdwg.org expected to generate BDQ RDF, or only publish BDQ-built RDF artifacts?**
2. **Must individual `bdqtest:` IRIs dereference through the full rs.tdwg.org negotiation model, or is dataset/static publication sufficient?**
3. **Should `bdqffdq.owl` be preserved verbatim as the authoritative ontology file, or transformed into rs.tdwg.org-native tables?**
4. **If `bdqtest` is normalized into linked CSV tables, are those tables publication artifacts generated from RDF, or will maintainers edit them directly?**
5. **Should rs.tdwg.org CI adopt BDQ-specific semantic validation such as SHACL/SPARQL checks, or should those remain only in the BDQ repository?**

The current BDQ build already includes consistency audits, vocabulary usage audits, and SPARQL template validation (`tg2/_make_review/do_build.sh:7-30`), and BDQ also has a SHACL validator script for `bdqtest.ttl` (`tg2/_build_review/tools/validate_bdqtest_against_shacl.py:5-20`, `85-87`).

## 12. Final conclusion

BDQ fits rs.tdwg.org **partly**, but not completely, within existing conventions.

It fits naturally where rs.tdwg.org already supports:

- publication of RDF/HTML via content negotiation;
- linked child-resource modeling through `linked-classes.csv`;
- dataset-oriented testing and publication structure.

It creates semantic and technical friction where rs.tdwg.org currently assumes:

- row/column metadata as the primary source format;
- one emitted property value per populated cell;
- automatic TDWG term/version/list/vocabulary/standard propagation from current-term tables;
- no native RDF/OWL passthrough for arbitrary ontology graphs.

Accordingly:

- `bdqffdq.owl` should be handled as an ontology-native artifact, preferably preserved and served directly.
- `bdqtest` can be brought closer to rs.tdwg.org’s native model by using linked classes for multiplicity, but those linked publication CSVs should ideally be **generated from RDF-maintained BDQ source** rather than becoming the primary editorial representation.

That approach preserves BDQ semantics while making best use of the architecture rs.tdwg.org already has.
