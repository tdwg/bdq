# Maintaining the BDQ standard

*Draft, started 2026-11-14, during the public review.* How the BDQ vocabularies, Tests, and documents are changed once they are accepted, and how changes are proposed. The design is in [`deployment_rs_tdwg_org.md`](../_make_review/deployment_rs_tdwg_org.md), Section 13.1; issue [#340](https://github.com/tdwg/bdq/issues/340) tracks the work. Parts of the workflow below are not yet implemented; they are marked *planned*.

## Two layers

| Layer | Where | What |
|---|---|---|
| **Accepted** | [tdwg/rs.tdwg.org](https://github.com/tdwg/rs.tdwg.org): during the review the `bdq-source` branch (inputs, in `process/bdq-revisions/`) and the `bdq` branch (processed, served at <https://bdq-public-review.rs.tdwg.org/>); after ratification `master`, under the rs.tdwg.org maintainers | The source of truth: the terms and versions of the seven vocabularies (`bdqdim`, `bdqenh`, `bdqcrit`, `bdquc`, `bdqval`, `bdqffdq`, `bdqtest`), the `bdqffdq` axioms, the GUID tables behind the Test graphs, and the metadata of the documents |
| **Proposed** | this repository, tdwg/bdq | Where changes are proposed, drafted, and reviewed: issues with markdown tables, draft rows, draft documents. Nothing here is authoritative until it is accepted and migrated into rs.tdwg.org |

The text of the documents (guides, supplement, tutorial, landing page, and the headers and footers of all documents) is maintained in this repository, in [`../_build_review/templates/`](../_build_review/templates/). Their metadata (titles, abstracts, authors and contributors with their roles, licence, dates, versions) is in rs.tdwg.org. See also the table of sources of truth in [`../README.md`](../README.md#where-the-bdq-standard-is-maintained-sources-of-truth).

## Files in this repository that are generated: do not edit

- `tg2/_review/vocabulary/*_term_versions.csv`, `tg2/_review/vocabulary/bdqffdq.owl`, `tg2/_review/dist/bdqffdq.*`, and the GUID tables in `tg2/core/` (`TG2_tests_additional_guids.csv`, `information_element_guids.csv`, `TG2_policy_guids.csv`, `TG2_citation_guids.csv`): exported from rs.tdwg.org by [`../_make_review/export_rs_baseline.py`](../_make_review/export_rs_baseline.py), which records the rs.tdwg.org commit in `tg2/_review/vocabulary/rs_tdwg_org_baseline.json`. The site build fails if they differ from rs.tdwg.org's `bdq` branch.
- `tg2/core/TG2_tests.csv`, `TG2_multirecord_measure_tests.csv`, and the rest of `tg2/_review/dist/`: generated from those by `copy_files.sh`.
- Everything else in `tg2/_review/` apart from its README: generated by `do_build.sh`.

## Changing accepted content

A change to the accepted state is a new release in rs.tdwg.org: a release directory `process/bdq-revisions/bdq-revisions-YYYY-MM-DD/` with release-input CSVs (only the changed rows), its `config.yaml`, and, where they change, the `bdqtest` GUID tables or the `bdqffdq` axioms; processed by `process.py`, and checked, before it is merged. The procedures:

- a Test: "Changing a Test" in [`process/bdq-revisions/README.md`](https://github.com/tdwg/rs.tdwg.org/blob/bdq-source/process/bdq-revisions/README.md) (on `bdq-source`);
- the `bdqffdq` axioms: [`process/process-ontology.md`](https://github.com/tdwg/rs.tdwg.org/blob/bdq-source/process/process-ontology.md), Section 5;
- terms of the other vocabularies and document metadata: [`process/process-vocabulary.md`](https://github.com/tdwg/rs.tdwg.org/blob/bdq-source/process/process-vocabulary.md) (a document whose content changes is marked `modified: true` in the release `config.yaml`).

Then bring this repository up to date, from `tg2/_make_review`:

```bash
python3 export_rs_baseline.py          # rs.tdwg.org branch bdq from GitHub; --rs <checkout> --ref <ref> for a local one
git diff                               # review: only what changed in rs.tdwg.org should change
./copy_files.sh && ./do_build.sh       # regenerate dist/ and the documents
```

and commit the export and the regenerated documents together.

## Versions and identifiers

- Term version IRIs have rs.tdwg.org's form, `https://rs.tdwg.org/{vocabulary}/terms/version/<local name>-<date>`. The SDS 2.3.2 form `…/terms/<local name>-<date>` redirects to it for the BDQ term lists.
- A Test has two dates. `issued` dates its latest version, the one the documents cite as its Term version IRI. `DateLastUpdated` is the date of its last substantive change, the change in behavior that implementations must follow: set it to the release date for such a change, and leave it unchanged for any other change.
- Implementations cite the version on `DateLastUpdated` in `@ProvidesVersion`: `https://rs.tdwg.org/bdqtest/terms/version/<uuid>-<DateLastUpdated>`. Tests that are not in the standard (Supplementary, older, or retired Tests) have no rs.tdwg.org IRI; implementations cite them as `urn:uuid:<uuid>`. How such Tests are versioned is open.
- UUIDs of Tests and of the nodes in their graphs (Methods, Specifications, Arguments, information elements, Policies, citations) never change and are never reused. UUIDs minted for a draft are kept when it is accepted.

## Proposing changes

- **Issues.** A proposed or changed Test is discussed in an issue of this repository with a markdown table, as before. [`bdq_issue_to_csv`](https://github.com/kurator-org/bdq_issue_to_csv) turns such tables into rows in the published BDQ column names.
- **A proposals file** *(planned)*: rows that differ from the exported baseline, in the published column names, with any new GUID-table entries.
- **New Use Cases and Tests** can be drafted with [`bdq_usecase_builder`](https://github.com/FilteredPush/bdq_usecase_builder), which follows the phases of the BDQ Tutorial; exporting its proposals as rows is *planned*.
- **The draft build** *(planned)*: builds draft Lists of Terms, the Quick Reference Guide, and `dist/` from the baseline plus the proposals, marked as draft, with document headers that say the document is a draft not yet issued.
- **Migration on acceptance** *(planned)*: a tool that turns accepted proposals into an rs.tdwg.org release directory, validated with `process.py --dry-run` and the Test-graph check; after processing, the baseline export brings the new state back here.

## The Test graphs

The graph of each Test (its Method, Specification, Arguments, information elements, citations, and Policies) is built by one builder: `process/bdq-revisions/bdqtest_rdf.py` in rs.tdwg.org (decided 2026-11-14). It generates the graph of each Test version served by rs.tdwg.org, and is to generate this repository's `dist/bdqtest.*` too, replacing kurator-ffdq and `tg2/_build_review/build_bdqtest_rdf.py` for the accepted state *(planned)*.

## Checks

- **The site build** (`.github/workflows/pages.yml`): the site's unit tests; the check that the generated files match rs.tdwg.org; then the build, whose audits and SPARQL checks must pass (`tg2/_build_review/tools/README.md`).
- **rs.tdwg.org**: `process.py --dry-run` before processing; after processing, review the diffs of the shared tables (only BDQ rows may change), run `bdqtest_graphs.py` and its check, and test a local Docker image (`index/dereferencing-test.py`).

## After ratification

The accepted layer moves to rs.tdwg.org `master`, under the rs.tdwg.org maintainers: the export then reads `master`, a real standard number replaces the placeholder `http://www.tdwg.org/standards/YYY`, the document URLs lose `/draft/`, and the review's placeholder versions, dated by the drafts, give way to real versions with the ratification date (`deployment_rs_tdwg_org.md`, Section 8.5). This README will change accordingly.
